# AI 导出优化研究与真实档案对比

本文由 Codex 于 2026-10-04 整理，供 Claude Code 独立复核。它汇总当前 AI 导出的真实文件对比、合成基准、进一步压缩实验，以及已经落实的 LF 换行优化。重点是区分文件字节、逻辑文本字符、估算 token 和模型理解准确率，避免把不同指标混为一谈。

核心结论：用户提供的真实档案中，AI_2 相比旧 AI_1 的文件大小减少 12.53%，逻辑文本字符减少 17.88%，输入 token 粗估减少 15.91%。两次抓取时间不同，这不是严格的同输入格式对照。进一步的低风险压缩候选收益较小；已实施 LF 换行规范化，在这份文件上再减少约 1.50% 字节，逻辑文本逐字一致。更大的 token 或理解准确率收益尚待目标模型验证。

本次修订纳入用户转交的 Claude Code 独立复核。基础数值得到交叉验证；同时修正了内容规范化、引用代价、Unicode 行边界及 token 口径的说明。U+2028/U+2029 归属风险已在当前渲染器修复，下面两份原始文件仍保持原状，表中数值描述的也是这两份原始文件。

## 输入与比较方法

以仓库根目录为基准，用户提供的输入为：

| 输入 | 本地位置模式 | 格式 | 文件内抓取时间 |
|---|---|---|---|
| 新版 | `Archives/*_全量快照_截至20261002_AI分析版.md` | `WEIBO_AI_2` | 2026-10-04 18:30+08:00 |
| 旧版 | `../WeiboTextArchiver_0.6.0_Windows/Archives/*_全量快照_截至20261001_AI分析版.md` | `WEIBO_AI_1` | 2026-10-02 00:46+08:00 |

两份文件都声明 `range=ALL`、自然结束和 `VISIBILITY_SCOPE=PUBLIC`。文件名中的“截至”是最新微博日期，不是抓取日期。

这里的真实新文件是 LF 修改前的用户导出，后文换行实验另以这份文件为基线。如果仅将已验证的 LF 变化应用于它，相对旧文件的字节减少约为 13.84%，不能把两个阶段的减少百分比直接相加。

比较分为三个层次：

1. 读取原始字节，统计磁盘文件大小；用 UTF-8 文本读取后统计规范化换行的逻辑字符数。
2. 解析顶层记录、评论、转发链、RT 正文和状态，分别解析旧版 `=RT` 与新版 `REF=Wn.OWN/RT` 引用。旧版引用按其首次正文定义解析，新版要求引用目标位于当前文件更早的记录。
3. 按发布时间和还原后的顶层文字匹配记录；同一分钟的两条记录用正文区分。还原过程考虑结构转义、`//@` 拆分和平台默认转发文本的 `NO_COMMENT` 表示。

两份 AI 文件没有完整暴露原微博 ID，因此这里是按时间与内容对应，不应描述成基于原始 ID 的逐条身份认证。字符一致性是在约定的格式还原与文本规范化之后比较的，不是整文件字节一致。

解析旧有这份 AI_2 文件时，需要按 `\n` 分行才能还原其原始结构。本轮最初的临时解析器使用 `str.splitlines()`，遇到了不带引用前缀的 RT 续行。最初将其只归为解析器问题不够完整：将 U+2028 等字符识别为换行的其他工具也会遇到相同情况，可能把他人原文当作无前缀的顶层文字。这是导出格式的归属风险，修复见后文。

## 进一步的无损压缩实验

以下实验以用户提供的新 AI 文件为输入，在内存或临时目录进行，没有改写原文件。

### 换行编码规范化

原文件采用 Windows CRLF。以统一的 LF 写出后：

| 指标 | 数值 |
|---|---:|
| 原始文件大小 | 514,997 字节 |
| LF 文件大小 | 507,278 字节 |
| 节省 | 7,719 字节，约 1.50% |
| 规范化换行后的逻辑文本 | 逐字一致 |
| 当前粗估 token | 不变 |

此项已经实施于 `weibo_archive/exporter.py` 的 `_atomic_write_text`：

```python
temp_path.write_text(text, encoding="utf-8", newline="\n")
```

它影响以后生成的 Markdown，不会追改既有归档，也不修改正文内的 U+2028 等字符。以用户文件通过真实写入函数生成临时输出，已确认逻辑文本一致、字节等于 UTF-8 编码后的逻辑文本、原输入未变。

这是存储格式优化，不是已证明的 token 或模型准确率提升。

此前“估算 token 不变”的比较使用的是读入后已规范化为 LF 的内存文本。若用同一估算器对磁盘原始字符计算，CRLF 文件为 203,397，LF 文件为 195,678，差额恰好是 7,719 个 CR。由于估算器机械地计入每个剩余字符，这个差额同样不是具体模型的真实分词差额。是否以及在哪一步规范化换行，还取决于文件读取或上传流程。

### Unicode 行边界与归属保护

Claude 指出了 W673 的 2 处 U+2028：旧完整排版会把它们拆成有 `> ` 前缀的行，而此前 AI_2 将其留在 RT 行内。如果后续编辑器或分块器把 U+2028 当换行，续行会失去引用前缀，产生静默的归属风险。这个问题优先于压缩收益。

当前修复采用与完整版引用处理一致的 `splitlines()` 行边界规则，先拆分再添加前缀：

- 完整 RT 正文与 RT 预览的每一行都获得引用前缀。
- 转发链的 Unicode 续行都保留链前缀。
- 顶层文字与顶层预览拆行后，结构形状的行继续执行转义，防止伪造记录头或 RT 标记。
- 空链段保留原有行为。

覆盖 U+2028、U+2029 以及同一规则支持的其他行分隔控制字符的回归检查已通过。对真实 W673 的 123 字符正文，修复后的引用输出与完整版 `quote_markdown` 一致，每条续行均带引用前缀。原文件没有被改写，修复对后续导出生效。

这项修复明确规范化了行分隔编码，不应被称为逐字节无损；目的在于保持正文行的归属边界。

### 结构分隔符的可逆原型

只把顶层和 RT 记录头中的全角 `｜` 换成半角 `|`，保留原始换行方式：

| 指标 | 数值 |
|---|---:|
| 原始大小 | 514,997 字节 |
| 原型大小 | 501,839 字节 |
| 节省 | 13,158 字节，约 2.55% |
| 逻辑字符数 | 不变 |
| 当前粗估 token | 195,678，保持不变 |

针对这份文件，先检查相关记录头没有原有的 ASCII 管道符，再执行转换及逆转换，确认能逐字节还原原文件。

这个证明只适用于当前样例。任意输入可能本来就含半角管道符，正式实现必须设计转义与解析规则，并同步说明、结构识别和测试。原型尚未并入应用，尚未验证目标模型的 token 数及理解效果。

注意：Python 默认文本读取会把 CRLF 规范化成 LF。最初若直接将读取的字符串重新 UTF-8 编码，会得到 507,278 字节，而不是原文件的 514,997 字节。最终分隔符实验已改用原始字节并保留换行，避免把换行节省混入分隔符收益；不能把这些中间值混为同一个基线。

### 重复正文与转发链

- 实际打印的完整 RT 正文中，存在 5 组完全重复内容；不计引用标记开销，最多再节省 769 字符，约占全文 0.33%。
- 这 5 组的正文长度与出现次数为 `(40, 2)`、`(36, 18)`、`(33, 2)`、`(20, 5)`、`(4, 2)`。它们多为短文本，不应据此预期大幅节省。
- 转发链有 24 组重复片段，不计引用与字典开销，最多省 357 字符，约占全文 0.15%。
- 一个每次引用与每项定义各按 15 字符计算的示意方案没有净收益；这只是该方案的估算，不是所有可能编码的最优性证明。

若未来跨微博 ID 复用相同正文，必须保留每次出现的作者、时间、媒体、状态及记录数量。相同字符不能用于合并作者身份或推断不同记录是同一微博。鉴于本次收益很小，尚未增加这类规则。

### 作者名称字典与读法说明

将所有 RT 作者显示名称替换为编号的字符预算试算，从 4,115 增至 4,793，即增加 678 字符。这里计入编号定义，未计额外读法说明。若仅应用于当前预算为正的 20 组，按本次标签长度方案可省约 1,356 字符，约 0.58%；这也不是最优编码或模型效果结论。

## token 估算与准确性的边界

本轮所有 token 数均来自项目现有 `estimate_tokens`，其规则为：ASCII 字母连续段按每四个字符估一 token，数字连续段按每三个字符估一 token，两类连续段分别向上取整；其余字符每个估一 token，ASCII 空格不计。

它没有对应具体模型的分词词表，因此：

- 不能把估算数当作实际账单或精确上下文用量。
- 全角与半角分隔符在这个公式中都算一个单位，公式无法评价它们的真实 token 差异。
- 英文结构、中文正文、多语言、数字和符号的实际分词差异，需要目标模型对应的方法验证。
- 当前粗估接近 20 万 token，也不能证明完整文件必定装入某个模型的上下文；提问、历史上下文和回答都需要空间。

Claude 提出将中文假设为每字 1.3–1.5 token 时，降幅可能约为 14.0%–14.7%。这是敏感性假设，不是目标模型的分词实测，也不是统计置信区间。本报告保留可复算的 15.91% 作为“现有公式的估算结果”，不将其改写成已验证的“约 14%–16%”，也不将由该公式得到的 18.9% 容量折算当作实际容量承诺。

已检查当前可用 Python 和 Node 环境，未找到 tiktoken、js-tiktoken、tokenizers 或 transformers 等可直接使用的分词库。本轮未为研究新增依赖。

需要区分两种准确性：程序层的内容、结构与引用一致性可以做确定性检查；模型的归属判断、证据检索和结论完整性需要问答评测。可逆编码不自动证明模型理解不会下降。
